# Paper reissue hands possession to the requester; return locked to the current holder

This change moves physical possession of a paper to the reissue requester once their reissue is accepted, and tightens the return path so only whoever currently holds the paper can return it. On reissue-accept the previously-ACCEPTED row is rewritten to `REISSUED BY <acceptor> TO <requester>` (shown in the Status column, not the rejection remark), and the reissue request itself becomes `ACCEPTED` with `reject_remarks` cleared to `null`. The backend `POST /return-requests` and the matching frontend pre-check now treat only `requested_by` of the active ACCEPTED entry as the holder, dropping the `issue_to` fallback so the old holder can no longer file a return. The All Requests table colors `REISSUED…` purple, and the Action column gets a `minWidth` plus `inline-block` buttons to keep the Del button on screen.

This pass re-verifies the six edits for local correctness; `node --check` and `vite build` pass clean.

**Watch for:** the fix only reaches the local Express backend — the production serverless handler (`api/index.js`) and the portable-app backend still run the old reissue/return logic, so a Vercel or Electron deploy would silently revert the behavior. Apply the same two backend edits there before deploying.

**Verdict**: APPROVED

## High-level view

A reissue request carries `requested_by` = the reissue requester (the intended new holder) and `issue_to` = the current holder who must approve it. On accept, the acceptor's own ACCEPTED row is rewritten to `REISSUED BY <acceptor> TO <requester>` and the reissue request flips to `ACCEPTED` with `reject_remarks: null`. `req.user.username` is the acceptor (old holder letting go) and `request.requested_by` is the requester who receives it, so the status string reads as a handoff chain in the Status column.

Both return paths now key the holder solely off `requested_by` of the ACCEPTED entry, dropping the `issue_to` fallback that previously let the old holder return; after a reissue the active entry has `requested_by` = the new holder and `issue_to` = the old holder, so the old holder is refused on both layers.

The edits land only in the local dev backend (`server/routes/orders.js`, proxied via Vite) and the dashboard. The deployed surfaces are untouched: `api/index.js` still writes `REISSUED TO <requester>` and keeps the `REISSUE BY <acceptor>` string remark, and its return check still allows `issue_to`; `portable-app/server/routes/orders.js` is in the same stale state. Local testing will therefore confirm the new behavior, but any deploy reverts it until those files are brought in line.

The Action column gets `minWidth: 65px` and the buttons become `display: inline-block`, which stops the Del button from being squeezed off-screen by a collapsing column. The cell still inherits `maxWidth: 200px` with `overflow: hidden` from `styles.td`, so Del is safe only while the three button labels combined stay under that cap — a label-dependent guarantee rather than a structural one.

<details><summary>Details</summary>

### Reissue-accept handoff and the status string

A reissue request is created with `requested_by` = the requester (new holder), `issue_to` = the current holder, and `reject_remarks: 'REISSUE'`. The accept branch keys on that marker and rewrites the old ACCEPTED row to `REISSUED BY ${req.user.username.toUpperCase()} TO ${request.requested_by.toUpperCase()}`, then sets the reissue request to `ACCEPTED` with `reject_remarks: null`. The acceptor is the old holder releasing the paper and the requester is the new holder receiving it, so the status string encodes the handoff chain and renders verbatim in the Status column. The new entry's `reject_remarks` is `null`, and the old entry's was already null (the non-reissue accept branch never writes it), so neither reissue row carries a rejection remark.

One data note that predates this diff: rows created before this change that still carry the historical `reject_remarks: 'REISSUE BY <x>'` value will keep rendering `ISSUE (R): REISSUE BY <x>` in the remark column until that legacy data is corrected.

### Return restricted to the requested_by holder

`POST /return-requests` now sets `holder = acceptedReqs[0].requested_by` and rejects when `holder !== actor`, with the `requester` variable and the `|| issue_to` fallback removed; the frontend Return pre-check mirrors it with `if (accepted.requestedBy !== actor)`. This is consistent with the rest of the app — the "already issued to" guard and the reissue `currentHolder` both resolve the holder as `requested_by || issue_to`, so `requested_by` is already the primary holder everywhere and the removed fallback was only a safety net. That fallback was the only thing tolerating a missing `requested_by`, which is what issue 4 turns on.

### The deployed backends were not updated

This is the headline gap, deferred by design — the user's brief is to verify locally before deploying. Locally, `vite.config.js` proxies `/api` to the Express server mounting `server/routes/orders.js`, so the edited file is what runs under `npm run dev`. In production, `vercel.json` rewrites `/api/(.*)` to `api/index.js`, whose accept handler (line 419) still writes `REISSUED TO ${request.requested_by.toUpperCase()}` and `reject_remarks: \`REISSUE BY ${req.user.username.toUpperCase()}\`` (a string, not null), and whose return check (line 428) still allows `issue_to`. `portable-app/server/routes/orders.js` is in the same stale state (lines 225–226 accept, 305–308 return). The same two edits must be applied to `api/index.js` — and to `portable-app` if that build ships — before deploying, or a deploy silently reverts.

### Del button: minWidth helps, the cap remains

The Action `<th>` and `<td>` now carry `minWidth: 65px`, which stops the column from collapsing so the Del button is no longer squeezed off-screen — the reported "sometimes not visible" symptom. The fragility is that the cell still spreads `styles.td` (`maxWidth: 200px`, `overflow: hidden`, `textOverflow: ellipsis`) plus the added `whiteSpace: nowrap`; Del is the rightmost of up to three buttons, so if their combined width exceeds 200px the right edge clips — the same symptom. Overriding `maxWidth` or `overflow` on the Action cell would make "always visible" structural rather than label-dependent.

### Test coverage

There is no automated suite for these flows; correctness is established by reading the code path. `node --check server/routes/orders.js` (exit 0) and `vite build` (exit 0, only the pre-existing >500 kB chunk-size warning) were re-run here. The user's planned local UI test is the real gate and exercises the Express backend, so it will not catch the `api/index.js` divergence. Not exercised: production behavior via `api/index.js`, the portable build, the null-`requested_by` edge, and Del clipping above ~200px.
