# Reissue transfers physical possession to the requester; status shows the handoff chain

This change reworks the paper reissue-accept flow so that accepting a reissue moves physical possession to the reissue requester. The previously-ACCEPTED entry is rewritten to a `REISSUED BY <acceptor> TO <requester>` status (shown in the Status column, not the rejection remark), and the reissue request itself becomes ACCEPTED with `reject_remarks` cleared to `null`. The return path is tightened so only the current holder — the `requested_by` of the active ACCEPTED entry — can submit a return, removing the old `issue_to` fallback. The All Requests table colors the REISSUED status purple, and the Action column gets a minimum width plus inline-block buttons to keep the Del button visible. The edits land only in the local Express backend (`server/routes/orders.js`) and the dashboard.

**Watch for:** the fix as written only takes effect against the local dev server — the production Vercel API (`api/index.js`) still runs the old reissue/return logic, so the new behavior won't ship until that file is updated; the Action column still caps at `maxWidth: 200px` with `overflow: hidden`, so Del can be clipped if button labels ever grow.

**Verdict**: NEEDS_CHANGES

## High-level view

The acceptor (current holder) accepting a reissue marks their own ACCEPTED row `REISSUED BY <acceptor> TO <requester>` and flips the reissue request to ACCEPTED with `reject_remarks: null`. This correctly makes the reissue requester the sole physical holder and keeps the chain visible in the Status column rather than the rejection-remark column. The 2-reissue limit still fires because the new status string still begins with `REISSUED`.

Both the backend `POST /return-requests` and the frontend pre-check now treat only `requested_by` of the ACCEPTED entry as the holder, dropping the `issue_to` fallback. After a reissue only the new holder can return; the old holder is refused on both client and server.

The edits target `server/routes/orders.js`, which the Vite dev proxy uses locally. `vercel.json` rewrites all `/api/(.*)` to `api/index.js`, which still carries the old `REISSUED TO <requester>` status, the `REISSUE BY <acceptor>` remark, and the `issue_to`-aware return check. So the reworked behavior will pass local testing but revert to the old behavior once deployed to Vercel.

The Action column gets `minWidth: 65px` and the buttons become `display: inline-block`, which reserve column space. The cell still inherits `maxWidth: 200px` and `overflow: hidden` with `whiteSpace: nowrap`, so the rightmost button (Del) is only safe while the combined button labels stay under roughly 200px.

### Reissue-accept handoff and the status string

A reissue request is created with `requested_by` = the reissue requester (the intended new holder), `issue_to` = the current holder, and `reject_remarks: 'REISSUE'`. On accept, the branch keyed on `request.reject_remarks === 'REISSUE'` rewrites the old ACCEPTED row to `REISSUED BY ${req.user.username.toUpperCase()} TO ${request.requested_by.toUpperCase()}` and sets the reissue request to `ACCEPTED` with `reject_remarks: null`. `req.user.username` is the acceptor (the current/old holder letting go of the paper) and `request.requested_by` is the reissue requester who receives it, so the chain reads `REISSUED BY <old holder> TO <new holder>` — matching the brief's direction.

The Status column renders `r.status` verbatim, so the chain lives there; the remark span is gated on `if (r.rejectRemarks)`, and the new entry's remark is `null`, as is the old entry's (the normal insert never sets `reject_remarks`), so neither reissue row shows a remark. The 2-reissue cap still holds: `reissueCount` counts rows whose status `startsWith('REISSUED')`, and `REISSUED BY X TO Y` still qualifies, so the limit is unchanged.

One data note, not introduced by this diff: rows created before this change that still carry the old `reject_remarks: 'REISSUE BY <x>'` value will keep rendering `ISSUE (R): REISSUE BY <x>` in the remark column until that historical data is corrected.

### Return restricted to the requested_by holder

The backend `POST /return-requests` now sets `holder = acceptedReqs[0].requested_by` and rejects when `holder !== actor`, with the `requester` variable and the `|| issue_to` fallback both removed. The frontend Return pre-check mirrors this exactly: `if (accepted.requestedBy !== actor)`. After a reissue the active ACCEPTED entry has `requested_by` = the new holder and `issue_to` = the old holder, so only the new holder can return; the old holder is refused on both layers.

The removed `|| issue_to` fallback was the only path that tolerated a missing `requested_by`. If any ACCEPTED row has a null or empty `requested_by` — only possible from legacy or manually-inserted data, since the app's inserts always set it — `holder` becomes `null` and `null !== actor` is true for everyone, so nobody can return that order. A quick check that no ACCEPTED `paper_requests` row has a null `requested_by` is worth doing before relying on the tighter check.

### The deployed backend (api/index.js) was not updated

This is the blocking gap. Locally, `vite.config.js` proxies `/api` to `http://localhost:5000`, which is the Express server in `server/index.js` mounting `server/routes/orders.js` — so the edited file is what runs when you `npm run dev`. In production, `vercel.json` rewrites `/api/(.*)` to `/api/index.js`, the serverless handler. That file still has the original logic: the old ACCEPTED entry becomes `REISSUED TO <requester>` (no acceptor in the string), the new entry keeps `reject_remarks: \`REISSUE BY <acceptor>\`` (a string, not null), and the return check still allows `issue_to`. `portable-app/server/routes/orders.js` is in the same un-updated state. Net effect: the local UI test will confirm the new behavior, but a Vercel deploy will silently revert to the old behavior. The same two edits need to be applied to `api/index.js` — and to `portable-app` if that build is distributed — before deploying.

### Del button: minWidth helps, the cap remains

The Action `<th>` and `<td>` now carry `minWidth: 65px`, and `tblBtn` gets `display: inline-block` (a no-op, since buttons are inline-block by default, so the shared `tblBtn` change is safe across tables). The real fragility is that the Action `<td>` still spreads `styles.td`, so it keeps `maxWidth: 200px`, `overflow: hidden`, and `textOverflow: ellipsis`, plus the newly-added `whiteSpace: nowrap`. Del is the rightmost of up to three buttons (`Change`, `Change Ret`, `Del`). With `whiteSpace: nowrap` the buttons form one line; if their combined width exceeds 200px, `overflow: hidden` clips the right edge — i.e. Del — which is exactly the "Del sometimes not visible" symptom. Current short labels total roughly 150px, so it renders correctly today. To make the fix robust instead of label-dependent, override `maxWidth` (or `overflow`) on the Action cell itself.

### Test coverage

There is no automated test suite for these flows; correctness is established by reading the code path, not by execution. `node --check` on `server/routes/orders.js` and `vite build` both pass (re-run independently here; only the pre-existing >500 kB chunk-size warning appears). The user's planned local UI test is the real gate, and it exercises the Express backend — so it will not catch the `api/index.js` divergence. Not exercised: production behavior via `api/index.js`, the null-`requested_by` edge, Del clipping above ~200px, and the historical `REISSUE BY` remark data still sitting in older rows.
