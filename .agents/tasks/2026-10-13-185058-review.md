# Preserve payment history across completed orders + inline history in daily report

Payments used to be deleted when an order moved Active→Completed, so completed orders lost their receipt history and a restore came back empty. This change keeps the `payments` rows alive past the parent `orders` row (via a one-time FK drop), teaches the move / restore / permanent-delete and the three payment endpoints to work against either the live `orders` row or the archived `deleted_orders.data` snapshot, and adds a Completed-tab Receipt button so admins / `can_edit_receipt` holders can view-add-edit-delete on completed orders. Separately, the daily emailed Excel now shows each order's payment history inline in the existing Received column (`DD.MM.YY  <amount>/-`, one per line, oldest-first) with wrapText. Backend changes in `api/index.js` are mirrored in `server/routes/orders.js`; `npm run build` and `node --check` on all four touched backend files pass.

Watch for: the FK-drop migration is manual (confirmed — user ran it per request "sql run kar di"); payment integrity now rests entirely on application code since the DB no longer enforces it (confirmed). An unrelated completed-import/export field-set expansion is bundled into the same branch (confirmed).

**Verdict**: APPROVED

## High-level view

The payment-preservation design hinges on dropping the `payments_order_id_fkey` constraint so a payment row can outlive the `orders` row it pointed at, keeping `order_id` as the stable link to `deleted_orders.original_id`. The migration is idempotent (`DROP CONSTRAINT IF EXISTS`) and manual-run, matching the user's "I ran the SQL" message. The trade-off is that referential integrity is now enforced only in application code across move, restore, and permanent-delete — all three were updated to keep `order_id` consistent, so no orphans are created on the happy paths.

The move handler stops deleting payments and only re-points them in the rare `original_id` collision branch. The three payment endpoints (POST/PUT/DELETE) now detect whether the order is live (`orders` row exists) or completed (`deleted_orders` snapshot) and recompute `received_amount`/`balance`/`percent_received` into the right place. Restore re-points payments to the new SERIAL id and recomputes; permanent-delete removes the payment rows. The `can_edit_receipt` gate stays on PUT/DELETE, RECEIPT_EDIT logging is preserved, and restore + permanent-delete remain admin-only. `api/index.js` and `server/routes/orders.js` are consistent.

The frontend adds a green Receipt button to completed rows gated by `isAdmin || canEditReceipt`, widens the Action column render to include `canEditReceipt`, and refreshes both the active and completed lists after a receipt save. PaymentForm needed no change because a mapped completed order already carries `id` (=original_id), `orderNo`, `client`, and `totalAmount`.

The daily report fetches payments once, builds an `order_id → payments[]` map sorted oldest-first, and swaps the Received cell value for a newline-joined `DD.MM.YY  <amount>/-` string, falling back to the stored number when an order has no payment rows. Active rows key on `o.id`, completed rows on `d.original_id`. wrapText is applied to the Received column on both sheets. No new sheet, no payments-count line, all other columns and sheets untouched.

The branch also carries a completed import/export field-set expansion (status, follow-up, installation, section-drawing, and related remark fields) that is outside the payment-history task scope.

### Move preserves payments, re-points only on the collision branch

`payments.order_id REFERENCES orders(id)` had no `ON DELETE` clause (default `NO ACTION`), which blocked deleting the parent `orders` row while payment rows remained. The migration drops `payments_order_id_fkey` with `IF EXISTS` and keeps `order_id` intact so it links to `deleted_orders.original_id`. The database no longer protects against orphans, so the move/restore/permanent-delete code is the only thing keeping `order_id` consistent — any future endpoint touching payments must honor that.

The move handler (`DELETE /api/orders/:id` and `router.delete('/:id')`) no longer runs `payments.delete().eq('order_id', ...)`. In the normal branch `delId === orders[0].id`, so payments keep their key and the GET `/deleted/all` view (which exposes `id = original_id`) lines up with the payment rows. In the rare branch where `original_id` collides and `delId` is bumped, payments are re-pointed with `update({ order_id: delId })` so they follow the archived key. Then the `orders` row is deleted, which the dropped FK now permits.

### Payment endpoints target orders OR the deleted_orders snapshot

POST/PUT/DELETE on `/api/orders/:id/payments` recompute `received = SUM(payments.amount WHERE order_id=id)` and then branch: if an `orders` row exists, totals are written there as before; otherwise the handler reads the `deleted_orders` snapshot by `original_id`, takes `total = data.total_amount ?? data.totalAmount ?? 0`, and writes `received_amount`/`balance`/`percent_received` back into `data` while spreading the rest of the snapshot. The completed branch adds `cacheDel('deleted_orders')` in `api/index.js`. The `can_edit_receipt` gate on PUT/DELETE and the RECEIPT_EDIT history logging in PUT are preserved in both backends.

### Restore re-links and recomputes; permanent-delete cleans up

Restore keeps the new-SERIAL-id approach (stripping `id`/`created_at`), then re-points payments with `update({ order_id: newId }).eq('order_id', routeId)` where the route id is the archived `original_id`, and recomputes totals on the new order from its payments. This closes the round-trip: an order can go Active→Completed→Active with all payment rows and correct totals intact. Permanent-delete now runs `payments.delete().eq('order_id', routeId)` before removing the `deleted_orders` row, so nothing is orphaned. Both remain admin-only.

### Frontend Receipt button and dual refresh

`Dashboard.jsx` adds `canEditReceipt = isAdmin || user.canEditReceipt`, widens the completed Action `<th>`/`<td>` render condition to `(isAdmin || canEditCompleted || canEditReceipt)`, and adds a green Receipt button gated `(isAdmin || canEditReceipt)` that opens PaymentForm. `handlePaymentSaved` now calls both `fetchOrders()` and `fetchDeletedOrders()` so an edited completed order's totals refresh. PaymentForm is unchanged and works because the mapped completed order carries `id` (=original_id), `orderNo`, `client`, and `totalAmount` — all read directly by the form, and all its `/api/orders/${order.id}/payments` calls resolve through the completed branch above.

### Daily report inline history matches the exact format

`api/cron-daily-report.js` adds `payments` as a fifth `Promise.all` fetch, builds `byOrderId` and sorts each list oldest-first by `date` (lexical compare on the YYYY-MM-DD text, which equals chronological). `fmtDate` yields zero-padded `DD.MM.YY` from the YYYY-MM-DD text (regex path) or a `Date` fallback. `fmtPayments(list, fallback)` returns the stored numeric received when there are no rows, else `list.map(p => \`${fmtDate(p.date)}  ${Number(p.amount||0)}/-\`).join('\n')` — date first, plain integer amount, trailing `/-`, newline-joined. Active rows key on `byOrderId[o.id]`, completed rows on `byOrderId[d.original_id]`. `wrapReceivedColumn` finds the Received header column and sets `alignment:{wrapText:true,vertical:'top'}` on each data cell; this works because the report imports `xlsx-js-style` (not plain `xlsx`), which honors cell `.s` styles. No new sheet, no payments-count line in the summary HTML, all other columns and the four sheets unchanged.
