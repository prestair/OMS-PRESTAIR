# Admin "request on behalf of" for paper issue/return

Admins can now place a paper issue or return request on behalf of another user. The behalf user becomes the real `requested_by` (the paper holder who can later return it), while the acting admin is recorded in a new `placed_by_admin` column so reports can mark the requester as `<full name> (admin)`. The change spans both backends (`api/index.js` production, `server/routes/orders.js` local/Electron mirror), the schema (`setupSupabase.js` + a manual migration file), the daily Excel cron, and the Dashboard UI (two admin-only autocompletes, an optional back-date input, and a `requesterLabel` helper applied at every requester display). Non-admin `onBehalfOf`/`requestDate` are ignored server-side in both backends.

**Watch for:** the `placed_by_admin` column must be applied manually in Supabase (`api/behalf-of-migration.sql`) before the `(admin)` marker populates in production — the workflow deliberately does not run it (confirmed). The back-date feature (optional admin `requestDate` → `created_at`) was added mid-task and is wired through both backends and both forms (confirmed).

**Verdict:** APPROVED

## High-level view

The admin gate lives server-side: both POST handlers derive `effectiveRequester` and `placedByAdmin` only when `req.user.role === 'admin' && onBehalfOf`, so a forged `onBehalfOf` from a non-admin collapses to the caller's own username. The two backends are byte-for-byte equivalent in behavior, which is the key maintenance risk this feature carries and it is honored here.

The holder guard on return is the behavioral heart of the user's scenario (helpdesk02 issued to sekar → sekar holds it → only sekar can return). The guard now compares against `actor` (the behalf user when an admin acts) rather than the raw caller, and keeps the original full-name holder message, so the recent full-name fix is not regressed.

The requester marker flows from one DB column through four `/all` mappers into a single frontend `requesterLabel` helper used at all five report surfaces (All Requests table, OR on-screen, OR export, OR print, ISSUED TO status) plus the daily Excel. Target cells (Issued By / Return To) stay plain, so the `(admin)` tag only ever decorates the holder.

Back-date is admin-gated the same way: a valid `requestDate` sets `created_at`, which is what every report derives the issue/request date from, so no report-side changes were needed.

### Admin gate and the forged-field defense

Both POST handlers read `onBehalfOf` from the body but only trust it behind `req.user.role === 'admin'`. In `api/index.js`:

```js
const effectiveRequester=(req.user.role==='admin'&&onBehalfOf)?onBehalfOf:req.user.username;
const placedByAdmin=(req.user.role==='admin'&&onBehalfOf)?req.user.username:null;
```

`server/routes/orders.js` carries the identical computation in its readable style. A non-admin sending `onBehalfOf` gets `effectiveRequester = their own username` and `placedByAdmin = null`, so there is no spoofing path and no stray marker. This is the correct fail-closed posture for a trust-boundary field, and it is mirrored in both backends — the one place where drift between the two files would be a real security gap.

### Return holder guard treats the behalf user as actor

The return POST computes `actor` the same admin-gated way and feeds it into the holder check:

```js
const holder = acceptedReqs[0].requested_by || acceptedReqs[0].issue_to
const requester = acceptedReqs[0].requested_by
if (holder !== actor && requester !== actor) {
  return res.status(400).json({ error: `Order ${orderNo} paper is with ${holder.toUpperCase()}, only they can submit a return request` })
}
```

This is exactly the semantics the user asked for: because the behalf user is written as `requested_by` at issue time, they are the `holder`, and a return placed on their behalf (or by them directly) passes while everyone else is blocked with the holder's name. The frontend pre-check mirrors it with `if (accepted.issueTo !== actor && accepted.requestedBy !== actor)` and keeps the full-name message `Paper is with ${getFullName(accepted.requestedBy || accepted.issueTo)}, only they can return`, so the recent full-name fix survives on both client and server.

### Requester marker: one column, four mappers, one helper

`placed_by_admin` surfaces as camelCase `placedByAdmin` in all four `/all` mappers (api paper, api return, orders.js `mapPaperReq`, orders.js inline return mapper). The frontend helper reads either shape, so it is resilient to mapper differences:

```js
const requesterLabel = (r) => getFullName(r.requestedBy || r.requested_by) + ((r.placedByAdmin || r.placed_by_admin) ? ' (admin)' : '')
```

It is applied at all five requester surfaces — All Requests table (`requesterLabel(r)`), OR on-screen (`requesterLabel(pr)`), OR export, OR print, and the three `ISSUED TO ${requesterLabel(latestIssue)}` status strings. The leftover plain `getFullName(r.requestedBy)` usages are the `orTabUserSearch` filter (explicitly out of scope), the "My Paper Requests" pending widget, and a reminders widget — none of which are the five report anchors. Target cells (Issued By / Return To) remain plain `getFullName`, so only the holder is decorated.

The daily Excel cron appends the marker on the requester cell only:

```js
'Requested By': (r.requested_by || '') + (r.placed_by_admin ? ' (admin)' : ''),
```

### Back-date (admin-gated created_at)

Added mid-task. Both POST handlers accept an optional `requestDate` and, only for admins with a parseable date, set `created_at`:

```js
const backDate=(req.user.role==='admin'&&requestDate&&!isNaN(new Date(requestDate).getTime()))?new Date(requestDate).toISOString():null;
// ...
.insert({ ..., ...(backDate ? { created_at: backDate } : {}) })
```

An invalid or non-admin `requestDate` falls through to the DB default `now()`. Reports derive issue/request date from `created_at` (OR report uses `acceptedAt || createdAt`; daily report reads `created_at`), so the back-date surfaces without any report-side change. Both forms gate the date input behind `isAdmin` and reset it on submit success alongside the behalf state.

### Schema and migration

`setupSupabase.js` adds `placed_by_admin TEXT` to both CREATE TABLE blocks for fresh installs. Existing databases are handled by `api/behalf-of-migration.sql` (two idempotent `ADD COLUMN IF NOT EXISTS` statements), which is intentionally left for the user to run in the Supabase SQL editor. Until it runs in production, the `placed_by_admin` key in the inserts will fail against the live table — this is the one operational gate before shipping.

### Verification

`node --check` passes on `api/index.js`, `api/cron-daily-report.js`, `server/routes/orders.js`, and `server/setupSupabase.js` (all exit 0). `npm run build` (Vite v5.4.21) exits 0. No automated tests exist in this project; verification is build + syntax check only, so the admin-gate and holder-guard behavior were confirmed by reading both backends and the two form handlers rather than by test execution.
